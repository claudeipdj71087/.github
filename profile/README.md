<p>账号分组听起来像管理动作，实质是参数设计。真正决定分组是否好用的，是几个字段怎么取值：分组维度、组内账号上限、出口与账号的绑定粒度、观察期长度、命名规则、变更登记方式。这六个字段定下来，后面半年的日常操作基本都是按表执行，很少需要临场判断。</p>

<h2>一、参数总表：先把六个字段写清楚</h2>
<p>不要一边用一边想。先在文档里把这六个字段列成表，给每个字段一个默认值，之后所有例外都记录在案。分组结构混乱，几乎都是因为字段从来没被明确定义过。</p>
<h3>六个字段分别管什么</h3>
<p>维度决定按什么切组，粒度决定切到多细，上限决定一组塞几个号，绑定粒度决定出口怎么分，观察期决定新号多久能进正式组，命名规则决定半年后还认不认得。前三个影响结构，后三个影响运维。</p>
<h3>默认值怎么定</h3>
<p>单人账号通常一组一号、一号一出口；小团队按项目切组、组内不超过五个号；有地区要求时再加一层地区后缀。默认值不求最优，只求一致，不一致才是混乱的源头。</p>

<h2>二、维度一：按项目切，边界画在哪</h2>
<p>按项目分组是最自然的一刀，但边界常常画错：有人按客户切，有人按用途切，结果同一个账号在两张表里都出现，出口被绑了两次。</p>
<h3>三条边界规则</h3>
<p>一个账号只属于一个组；一个组只对应一条出口（或一组固定出口）；跨项目共用的账号单独建"共用组"，不要图省事塞进任一项目。这三条能解决九成的归属争议。</p>
<h3>什么时候允许共用出口</h3>
<p>只读、低频、无身份连续要求的用途可以共用；涉及登录、订阅、支付的一律单独绑。判断标准很简单：这个动作出错后能否靠重试解决，能就是低频，不能就是关键。</p>

<h3>组内上限为什么重要</h3>
<p>一组塞太多号，任何一次出口异常都会同时影响全部账号，排查时无法区分是个体问题还是组问题。把上限压到五个以内，风险半径就小了，代价只是多几条出口。</p>

<h2>三、维度二：按地区切，与项目维度怎么叠加</h2>
<p>地区维度不是必须的，但只要账号资料里写了具体地区，它就会变成一个隐性约束。叠加方式决定了台账好不好查。</p>
<h3>两级命名法</h3>
<p>用"项目-地区"两级命名，例如 <code>projA-usw-01</code>。项目在前便于按业务筛选，地区在后便于按地理聚合。序号用两位数字，别用日期，日期会让人误以为是创建时间而非顺序。</p>
<h3>粒度到州还是到城市</h3>
<p>多数情况到州就够，因为住宅出口的城市归属偶尔会有几个城市的偏移，要求到城市会频繁触发"不匹配"的告警。若账号资料填到具体城市，才把粒度下沉到城市，并在台账里备注容差范围。</p>

<h2>四、维度三：新老号分层，阈值怎么定</h2>
<p>新号和老号的风险特征不同，混在一组会让新号的问题污染老号的记录。分层不必复杂，两级就够：观察组和正式组。</p>
<h3>观察期设多长</h3>
<p>建议 14 天。短于 7 天，很多问题还没暴露；长于 30 天，账号长期挂在临时出口上，反而增加后期迁移成本。观察期内固定出口、固定设备、不做高敏感动作。</p>
<h3>老号什么时候降级</h3>
<p>出现连续两次验证、或一次登录态异常，就降回观察组观察一周，而不是直接换线。降级的目的是观察，换线是最后手段，两者别混。</p>

<h2>五、出口绑定：一号一出口还是一组一出口</h2>
<p>绑定粒度是最花钱的一个决定。绑得越细，成本越高、隔离越好；绑得越粗，省钱但故障会扩散。</p>
<h3>三种绑定模型的取舍</h3>
<p>一号一出口隔离最好，出口数量等于账号数量；一组一出口成本低，但组内互相影响；混合模型是关键号单独绑、边缘号共享，实践中用得最多。静态住宅出口月费大致在 60 至 200 元一条（仅供参考），账号数上到两位数时，混合模型通常能把支出压掉三到四成。</p>
<h3>变更登记要记什么</h3>
<p>谁改的、什么时候改的、从哪条出口换到哪条、原因是什么。四个字段，一条流水。没有这行记录，三个月后没人说得清某次异常是不是换线引起的。</p>

<h2>常见问答</h2>
<h3>组内账号能不能共用一个浏览器容器？</h3>
<p>答：不建议。容器共用会让指纹和本地存储互相污染，分组的意义就没了。至少做到一号一容器，出口和容器一一对应，台账里也按这个对应关系记录。</p>
<h3>地区维度可以省掉吗？</h3>
<p>答：如果账号资料里没有填具体地区，可以省。但只要涉及订阅支付、资料里写了州或城市，就建议保留地区后缀，否则换线时很容易绑错地区。</p>
<h3>一个账号换了项目，怎么处理？</h3>
<p>答：改归属可以，但不要同时换出口。先改台账与命名，观察一周，再决定是否换线。两件事一起做，出问题时无法判断是哪一步引起的。</p>
<h3>分组之后还需要人工巡检吗？</h3>
<p>答：需要，但频率可以降低。分组降低了排错难度，不能替代观察。建议每周看一次各组的中断与验证记录，异常集中在某一组时再深入排查。</p>
